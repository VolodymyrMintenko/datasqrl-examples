# Orders revenue pipeline

## Goal

Ingest order events from Kafka in real time and serve hourly revenue per product through an API, so
that merchandising and finance can see how each product is earning during the current day rather
than waiting for a nightly batch.

## Scope

**In scope:** the `orders` Kafka topic as the only source, deduplication of retried order events,
hourly revenue per product, and a queryable API over that aggregate.

**Out of scope:** order refunds and cancellations, currency conversion, customer or basket level
analytics, historical backfill from the data warehouse, and any write path. The API is read only.

## Functional requirements

- **FR-1**: Ingest the `orders` Kafka topic continuously; an order is reflected in the API within 30
  seconds of being produced.
- **FR-2**: Deduplicate orders on `order_id`, keeping the copy with the latest `ordered_at`.
- **FR-3**: Compute revenue per product per hour as the sum of `quantity * unit_price` over the
  order lines of the deduplicated orders, grouped by `product_id` and by the hour of `ordered_at`.
- **FR-4**: Expose a query that returns hourly revenue per product, filterable by `product_id` and
  by a time range, ordered by hour descending.
- **FR-5**: Recompute an already emitted hour when an order arrives up to 5 minutes after that
  hour's watermark has passed.
- **FR-6**: An order whose `ordered_at` is older than the lateness tolerance is dropped from the
  aggregate rather than counted in the wrong hour, and remains visible in the ingested order table.

## Sources

### `orders`

- **Transport**: Kafka topic `orders`.
- **Format**: JSON, no schema registry.
- **Sample payload**:
  ```json
  {
    "order_id": "8f3c1e94-2b77-4f1a-9a55-0d21c4b7e001",
    "customer_id": "c-10457",
    "ordered_at": "2026-09-30T11:42:07.482Z",
    "currency": "USD",
    "items": [
      { "product_id": "p-3391", "quantity": 2, "unit_price": 12.50 },
      { "product_id": "p-1120", "quantity": 1, "unit_price": 89.00 }
    ]
  }
  ```
  `customer_id` is nullable for guest checkout. `currency` is optional and defaults to `USD`.
  `items` is never empty. `unit_price` is the price actually charged, net of discounts.
- **Volume and rate**: ~40 orders/sec average, ~400/sec peak during promotions, ~3.5M orders/day.
- **Delivery guarantee**: at-least-once; the topic retains 7 days and can be replayed.
- **Duplicates and ordering**: a producer retry emits the same `order_id` again. Order is guaranteed
  per partition, and the topic is partitioned by `order_id`.
- **Updates**: records are immutable events, not CDC or upserts.

## Time semantics

- **Event-time field**: `ordered_at`, RFC3339 with milliseconds, UTC.
- **Lateness**: 5 minutes. An event later than that is excluded from the aggregate (FR-6).
- **Processing time acceptable?**: no, every aggregate is on event time.

## Entities and keys

- **Order**: primary key `order_id`, event time `ordered_at`. One order has many order lines.
- **OrderLine**: the flattened `items` array, identified by `order_id` plus `product_id`.
- **Product**: referenced by `product_id` only. No product dimension table exists in this project, so
  the API returns the id rather than a name.

No shared data catalog is present in this repository, so the source table is declared in the project.

## Transformations and aggregations

1. **Deduplicated orders.** Input: the `orders` topic. Key: `order_id`. Keep the row with the latest
   `ordered_at`.
2. **Order lines.** Input: deduplicated orders, flattened over `items`. Adds
   `revenue = quantity * unit_price` per line.
3. **Hourly revenue per product.** Input: order lines. Grouping: `product_id` and a 1 hour tumbling
   window on `ordered_at`. Aggregates: `sum(revenue)` as `revenue`, `sum(quantity)` as `units`,
   `count(distinct order_id)` as `orders`. A late event inside the 5 minute tolerance updates the
   already emitted hour; a later one is excluded.

## API surface

- **Queries**:
  - `HourlyProductRevenue(product_id: String, from_hour: DateTime, to_hour: DateTime, limit: Int)`
    returning `{ product_id, hour, revenue, units, orders }`, ordered by `hour` descending. All
    parameters optional; with none it returns the most recent hours across products.
  - `Orders(order_id: String)` returning the deduplicated order, for spot checks.
- **Mutations**: none.
- **Subscriptions**: none.
- **Access**: public within the internal network for this iteration. No tenant field exists in the
  payload.

## Test data and acceptance criteria

- **Test data**: at least 3 hours of orders across 3 products, and these edge cases: a duplicate
  `order_id` with a later `ordered_at`, an order arriving 2 minutes late (inside tolerance), an order
  arriving 20 minutes late (outside tolerance), an order with `customer_id` null, an order with no
  `currency`, a multi line order whose lines hit two different products, and an hour with no orders
  for one of the products.
- **Acceptance criteria**:
  - *(FR-2)* Given two records with the same `order_id` and different `ordered_at`, the deduplicated
    order table returns exactly one row, the one with the later `ordered_at`.
  - *(FR-3)* Given the multi line order above, hourly revenue contains one row per `product_id` for
    that hour, each with `revenue` equal to `quantity * unit_price` of its line.
  - *(FR-4)* Querying with `product_id` set returns only that product's hours, newest first.
  - *(FR-5)* The order arriving 2 minutes late changes the `revenue` of the already emitted hour.
  - *(FR-6)* The order arriving 20 minutes late does not change any hour's `revenue`, and is still
    returned by the `Orders` query.
  - *(FR-1)* An order produced to the topic is returned by the API within 30 seconds in the test run.

## Non-functional requirements

- **Freshness / latency**: 30 seconds from produce to queryable, measured from the Kafka record
  timestamp to the API response.
- **Throughput**: sustained 40 orders/sec, peak 400/sec. Above peak the pipeline may lag but must not
  drop records.
- **Retention**: hourly aggregates kept 13 months; deduplicated orders kept 30 days.
- **PII and sensitive fields**: `customer_id` is pseudonymous and must not be exposed by the API.
  No names, emails or addresses are in the payload.
- **Compliance**: none stated for this iteration.
- **Availability**: a redeploy may pause the API for under a minute; no data loss is acceptable.

## Open Questions

- **Should refunds and cancellations reduce revenue?** Recommended default: *no, out of scope for
  this iteration; revenue is gross of refunds.* Impact if wrong: high.
- **Are `unit_price` values already net of discounts and tax exclusive?** Recommended default:
  *net of discounts, tax exclusive.* Impact if wrong: high.
- **Is the hour boundary UTC or a business timezone?** Recommended default: *UTC.* Impact if wrong:
  medium.
- **Do multi currency orders exist?** Recommended default: *no, everything is USD and `currency` is
  ignored.* Impact if wrong: medium.
- **Is a product dimension needed for names?** Recommended default: *no, the API returns
  `product_id`.* Impact if wrong: low.
