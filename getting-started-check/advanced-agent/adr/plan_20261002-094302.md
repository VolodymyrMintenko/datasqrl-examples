## Requirements Summary

Build a new DataSQRL streaming pipeline that ingests the `orders` Kafka topic (JSON, no schema registry), deduplicates retried order events on `order_id`, flattens each order's `items` array into order lines with `revenue = quantity * unit_price`, aggregates revenue per `product_id` per 1-hour tumbling window on event time `ordered_at`, and serves the result plus a single-order lookup through a read-only API. Event-time lateness tolerance is 5 minutes and is implemented by the source watermark: events inside the tolerance still land in their hour, events beyond it are dropped by the window operator while remaining visible in the deduplicated order table.

Concretely the project delivers: `connectors/sources.sqrl` (schema table), `connectors/sources-prod.sqrl` (external `kafka-safe` connector over topic `orders`), `connectors/sources-test.sqrl` (filesystem connector over `connectors/test-data/orders.jsonl`), the main script `orders_revenue.sqrl` (dedup, order lines, hourly revenue, the two API functions, data-quality and observability tables, `/*+test */` snapshot tables), the configuration files `orders_revenue-shared-package.json`, `orders_revenue-test-package.json`, `orders_revenue-prod-package.json`, the test data file, `run-tests.sh`, and `README.md`.

Engines: `flink` (stream processing), `postgres` (serving the two query endpoints and the DQ/OB tables), `vertx` (GraphQL/REST/MCP server). No mutations, no subscriptions, no Iceberg, no Kafka engine — the Kafka topic is an **external** connector source, not a DataSQRL-managed internal table.

**UI assessment**: the requirements define an API surface only ("queryable API", two queries, no mutations, no subscriptions) and name merchandising/finance as consumers of query results, with no dashboard, chart, or screen requested. No UI is in scope, so no `/implement-ui` step appears in the checklist.

## Requirements Reference

Source document: `adr/requirements_20260930-135454.md`. Full text of every identifier cited in this plan:

**Functional requirements**

- **FR-1** — Ingest the `orders` Kafka topic continuously; an order is reflected in the API within 30 seconds of being produced.
- **FR-2** — Deduplicate orders on `order_id`, keeping the copy with the latest `ordered_at`.
- **FR-3** — Compute revenue per product per hour as the sum of `quantity * unit_price` over the order lines of the deduplicated orders, grouped by `product_id` and by the hour of `ordered_at`.
- **FR-4** — Expose a query that returns hourly revenue per product, filterable by `product_id` and by a time range, ordered by hour descending.
- **FR-5** — Recompute an already emitted hour when an order arrives up to 5 minutes after that hour's watermark has passed.
- **FR-6** — An order whose `ordered_at` is older than the lateness tolerance is dropped from the aggregate rather than counted in the wrong hour, and remains visible in the ingested order table.

**Scope statements**

- **SC-IN** — In scope: the `orders` Kafka topic as the only source, deduplication of retried order events, hourly revenue per product, and a queryable API over that aggregate.
- **SC-OUT** — Out of scope: order refunds and cancellations, currency conversion, customer or basket level analytics, historical backfill from the data warehouse, and any write path. The API is read only.

**Time semantics**

- **TS-1** — Event-time field: `ordered_at`, RFC3339 with milliseconds, UTC.
- **TS-2** — Lateness: 5 minutes. An event later than that is excluded from the aggregate (FR-6).
- **TS-3** — Processing time acceptable? no, every aggregate is on event time.

**Entities and keys**

- **EK-1** — Order: primary key `order_id`, event time `ordered_at`. One order has many order lines.
- **EK-2** — OrderLine: the flattened `items` array, identified by `order_id` plus `product_id`.
- **EK-3** — Product: referenced by `product_id` only. No product dimension table exists in this project, so the API returns the id rather than a name.

**Transformations and aggregations**

- **TR-1** — Deduplicated orders. Input: the `orders` topic. Key: `order_id`. Keep the row with the latest `ordered_at`.
- **TR-2** — Order lines. Input: deduplicated orders, flattened over `items`. Adds `revenue = quantity * unit_price` per line.
- **TR-3** — Hourly revenue per product. Input: order lines. Grouping: `product_id` and a 1 hour tumbling window on `ordered_at`. Aggregates: `sum(revenue)` as `revenue`, `sum(quantity)` as `units`, `count(distinct order_id)` as `orders`. A late event inside the 5 minute tolerance updates the already emitted hour; a later one is excluded.

**Non-functional requirements**

- **NFR-1 (Freshness / latency)** — 30 seconds from produce to queryable, measured from the Kafka record timestamp to the API response.
- **NFR-2 (Throughput)** — sustained 40 orders/sec, peak 400/sec. Above peak the pipeline may lag but must not drop records.
- **NFR-3 (Retention)** — hourly aggregates kept 13 months; deduplicated orders kept 30 days.
- **NFR-4 (PII and sensitive fields)** — `customer_id` is pseudonymous and must not be exposed by the API. No names, emails or addresses are in the payload.
- **NFR-5 (Compliance)** — none stated for this iteration.
- **NFR-6 (Availability)** — a redeploy may pause the API for under a minute; no data loss is acceptable.

**Open questions and their recommended defaults (adopted as decisions, see `## Assumptions`)**

- **OQ-1** — Should refunds and cancellations reduce revenue? Recommended default: no, out of scope for this iteration; revenue is gross of refunds. Impact if wrong: high.
- **OQ-2** — Are `unit_price` values already net of discounts and tax exclusive? Recommended default: net of discounts, tax exclusive. Impact if wrong: high.
- **OQ-3** — Is the hour boundary UTC or a business timezone? Recommended default: UTC. Impact if wrong: medium.
- **OQ-4** — Do multi currency orders exist? Recommended default: no, everything is USD and `currency` is ignored. Impact if wrong: medium.
- **OQ-5** — Is a product dimension needed for names? Recommended default: no, the API returns `product_id`. Impact if wrong: low.

## Source Payloads & Schemas

### Source: `orders`

- **Transport** — Kafka topic `orders`.
- **Format** — JSON, no schema registry. The body is the bare order object (no envelope).
- **Sample payload** (verbatim from the requirements):

```json
{
  "order_id": "8f3c1e94-2b77-4f1a-9a55-0d21c4b7e001",
  "customer_id": "c-10457",
  "ordered_at": "2026-09-30T11:42:07.482Z",
  "currency": "USD",
  "items": [
    { "product_id": "p-3391", "quantity": 2, "unit_price": 12.50 },
    { "product_id": "p-1120", "quantity": 1, "unit_price": 89.00 }
  ]
}
```

  Requirements notes, verbatim: "`customer_id` is nullable for guest checkout. `currency` is optional and defaults to `USD`. `items` is never empty. `unit_price` is the price actually charged, net of discounts."

- **Field table**

| Field | Type | Required | Nullable | Notes |
|---|---|---|---|---|
| `order_id` | STRING | yes | no | Primary/dedup key (EK-1, FR-2). Kafka partition key. |
| `customer_id` | STRING | no | yes (guest checkout) | Pseudonymous PII — must never be exposed by the API (NFR-4). Carried as a hidden column only. |
| `ordered_at` | TIMESTAMP_LTZ(3) | yes | no | Event time (TS-1), RFC3339 with milliseconds, UTC. Watermark column; hour grouping key source (FR-3). |
| `currency` | STRING | no | yes (defaults to `USD`) | Ignored for revenue (OQ-4); used only by the currency data-quality capture. |
| `items` | ARRAY of OrderItem | yes | no | Never empty. Flattened into order lines (TR-2, EK-2). |

- **Nested types** — `items` is `ARRAY<ROW<product_id STRING NOT NULL, quantity INT NOT NULL, unit_price DECIMAL(10,2) NOT NULL>>`:

| Nested field | Type | Required | Nullable | Notes |
|---|---|---|---|---|
| `items[].product_id` | STRING | yes | no | Grouping key for the hourly aggregate (FR-3, EK-3). |
| `items[].quantity` | INT | yes | no | Metric input: `sum(quantity)` as `units` (TR-3). |
| `items[].unit_price` | DECIMAL(10,2) | yes | no | Metric input: `revenue = quantity * unit_price` (TR-2). Net of discounts, tax exclusive (OQ-2). Sample values `12.50` and `89.00` have 2 decimal places. |

- **Delivery semantics** — at-least-once; the topic retains 7 days and can be replayed. A producer retry emits the same `order_id` again. Order is guaranteed per partition, and the topic is partitioned by `order_id`. Records are immutable events, not CDC or upserts. Deduplication key: `order_id`; tiebreaker: latest `ordered_at` (FR-2 / TR-1).
- **Volume and rate** — ~40 orders/sec average, ~400/sec peak during promotions, ~3.5M orders/day (NFR-2).
- **Constraints from out-of-scope features** — refunds/cancellations and currency conversion are out of scope (SC-OUT), but `currency` must remain a column on the ingested order so a later iteration can convert without re-modelling the source; `customer_id` must be ingested (it is part of the payload and needed for any future customer analytics) yet excluded from every API-exposed projection (NFR-4). There is no write path: no mutation table, so the Kafka source is an **external** connector table, never a DataSQRL-managed internal `/*+engine(kafka) */` table.

## API Contract

The API is **read only** (SC-OUT): no mutations, no subscriptions. Protocols: GraphQL, REST and MCP generated from the SQRL definitions (`compiler.api.protocols`). Access is public within the internal network for this iteration; no tenant field exists in the payload, so no authorization filter is applied.

The requirements state the surface, verbatim:

```
- Queries:
  - HourlyProductRevenue(product_id: String, from_hour: DateTime, to_hour: DateTime, limit: Int)
    returning { product_id, hour, revenue, units, orders }, ordered by hour descending. All
    parameters optional; with none it returns the most recent hours across products.
  - Orders(order_id: String) returning the deduplicated order, for spot checks.
- Mutations: none.
- Subscriptions: none.
- Access: public within the internal network for this iteration. No tenant field exists in the
  payload.
```

### Operation 1 / `HourlyProductRevenue`

- SQRL table function named `HourlyProductRevenue` with nullable (optional) arguments `product_id STRING`, `from_hour TIMESTAMP_LTZ(3)`, `to_hour TIMESTAMP_LTZ(3)`.
- Semantics: when an argument is null the corresponding filter is not applied; `from_hour` is an inclusive lower bound on `hour`, `to_hour` an inclusive upper bound; results are ordered by `hour` descending, then `product_id` ascending as a deterministic tiebreaker.
- Returned fields, exactly these names: `product_id` (String), `hour` (DateTime / TIMESTAMP_LTZ(3), the start of the 1-hour tumbling window in UTC), `revenue` (DECIMAL), `units` (INT/BIGINT), `orders` (BIGINT).
- `limit`: DataSQRL generates `limit` (and `offset`) arguments on the generated query endpoint, so the requested `limit: Int` parameter is served by the generated argument rather than a declared function argument. This is the only deviation from the parameter list in the requirements and is recorded in `## Technical Decisions`.
- REST/MCP: generated from this query (`Get`-prefixed MCP tool, GET endpoint under `rest/queries`).

### Operation 2 / `Orders`

- SQRL table function named `Orders` with nullable (optional) argument `order_id STRING`; when null, the function returns deduplicated orders ordered by `ordered_at` descending (spot-check listing), when set it returns the single deduplicated order with that id.
- Returned fields: `order_id` (String), `ordered_at` (DateTime), `currency` (String), `items` (list of `{ product_id, quantity, unit_price }`).
- **`customer_id` is never returned** (NFR-4): it exists on the ingested table as a hidden column only.

### Not exposed

Intermediate tables (raw ingest projection, deduplicated-stream projection used by the aggregate, order lines) are `_`-prefixed and absent from the API. The data-quality and observability tables defined in `## Data Quality & Observability` are exposed as their own query endpoints with optional filter arguments.

## Scenario Analysis

**Axis 1 / artifact type: `pipeline`.** The deliverable ingests an external Kafka source, deduplicates and aggregates it, and exposes a GraphQL/REST/MCP API. The artifacts are `.sqrl` scripts plus `*-package.json` configuration. It is not a catalog: there is no shared schema repository to build, no `{dataset}.sqrl` `_schema`-only governance layer consumed by multiple pipelines, and no ontology; the requirements explicitly state no shared catalog exists in the repository and the source is declared in the project.

**Axis 2 / task type: `new-project`.** The project folder contains no `.sqrl` file, no `*-package.json`, no connectors and no tests / snapshots. Everything / scaffolding, connectors, pipeline logic, API, test data, test runner, documentation / is created from scratch, which is the definition of `new-project` rather than `extend-project` (no existing pipeline to modify) or `connector-setup` (the work is not limited to connectors). It is not `architecture-design`: the requirements already fix the source, the transformation chain, the time semantics and the API surface, so the remaining design decisions are local (window type, dedup operator form, engine set) rather than an open architecture exploration.

**Answers to the `new-project` questions:**

- *Data sources*: one source, the Kafka topic `orders`, JSON without schema registry, external connector (`kafka-safe` with `flexible-json`), event time `ordered_at` with a 5-minute out-of-orderness watermark; a filesystem stand-in over `connectors/test-data/orders.jsonl` for the test environment.
- *Processing and aggregations*: dedup on `order_id` (TR-1), flatten `items` to order lines with `revenue` (TR-2), 1-hour tumbling window per `product_id` with `sum(revenue)`, `sum(quantity)`, `count(distinct order_id)` (TR-3).
- *API*: two read-only query functions, `HourlyProductRevenue` and `Orders`, as detailed in `## API Contract`; GraphQL plus generated REST and MCP.
- *Engines*: `flink`, `postgres`, `vertx`. Kafka engine is not enabled / the topic is an external connector, and there are no subscriptions or mutations. Iceberg and its query engines are not needed: retention of 13 months of hourly aggregates per product is small enough for Postgres.
- *Closest template*: `/opt/sqrl_templates/event_processing/` / realtime event ingest, `connectors/sources*.sqrl` layout, dedup, windowed aggregation, Postgres-served API, `run-tests.sh`, shared/test/prod package split.
- *UDFs*: none. Every transformation (multiplication, sum, count distinct, array flattening, tumbling window, timestamp bucketing) is expressible in Flink SQL/SQRL.

## Acceptance Criteria

The requirements state these criteria verbatim; each is followed by the concrete expected value from `## Test Data Specification`, which is the test oracle.

- *(FR-2)* "Given two records with the same `order_id` and different `ordered_at`, the deduplicated order table returns exactly one row, the one with the later `ordered_at`." 
  Expected: R1 and R4 both carry `order_id` `O-001`; the deduplicated order table returns exactly one `O-001` row with `ordered_at` `2026-09-30T10:06:30.000Z`. The hour-10 `p-3391` cell has `orders` = 2 and `revenue` = 37.50 (not 62.50).
- *(FR-3)* "Given the multi line order above, hourly revenue contains one row per `product_id` for that hour, each with `revenue` equal to `quantity * unit_price` of its line." 
  Expected: R3 (`O-003`, hour `2026-09-30T10:00:00Z`) contributes 12.50 to the `p-3391` row (1 × 12.50) and 30.00 to the `p-1120` row (3 × 10.00); the two products are separate rows for that hour.
- *(FR-4)* "Querying with `product_id` set returns only that product's hours, newest first." 
  Expected: `HourlyProductRevenue(product_id: "p-3391")` returns exactly three rows in this order: hour `2026-09-30T12:00:00Z` revenue 25.00 units 2 orders 1; hour `2026-09-30T11:00:00Z` revenue 50.00 units 4 orders 1; hour `2026-09-30T10:00:00Z` revenue 37.50 units 3 orders 2. No `p-1120` or `p-7742` row appears.
- *(FR-5)* "The order arriving 2 minutes late changes the `revenue` of the already emitted hour." 
  Expected: R8 (`O-007`, `ordered_at` `2026-09-30T12:13:00.000Z`, delivered after the 12:15 record) is included, so hour `2026-09-30T12:00:00Z` for `p-3391` has `revenue` 25.00, `units` 2 and `orders` 1 rather than no row at all.
- *(FR-6)* "The order arriving 20 minutes late does not change any hour's `revenue`, and is still returned by the `Orders` query." 
  Expected: R9 (`O-008`, `ordered_at` `2026-09-30T11:55:00.000Z`, revenue 178.00) appears in **no** aggregate row — hour `2026-09-30T11:00:00Z` contains only `p-3391` 50.00 and `p-7742` 14.50 — while `Orders(order_id: "O-008")` returns the order with `ordered_at` `2026-09-30T11:55:00.000Z`, `currency` `USD` and its single item `p-1120` `quantity` 2 `unit_price` 89.00.

## Data Quality & Observability

There is no data catalog in this repository and no sibling pipeline, so there are **no upstream guarantees to trust and no existing coverage to reuse**. The single source is a raw Kafka topic carrying JSON without a schema registry, at-least-once, with producer retries. Everything this job relies on about the payload is therefore unverified at the boundary, and the checks below are limited to the conditions that would silently corrupt this job's one result: revenue per product per hour.

**Build**

- **DQ_OrderLine_Invalid_Amount** (data quality). Input: the flattened order lines of the deduplicated order stream, before they enter the revenue path. One row is one order line whose `quantity` is less than or equal to zero or whose `unit_price` is negative, carrying `order_id`, `product_id`, `quantity`, `unit_price` and `ordered_at`, ordered by `ordered_at` descending then `order_id` and `product_id` ascending, filterable by `product_id` and `order_id`. Impact on this job: such a line would subtract from or distort `revenue` and `units` for a product-hour, and because revenue is a sum nobody would see which line caused it. The condition can occur because the topic has no schema registry and no catalog assertion guarantees positive amounts, and because the requirements only state that `unit_price` is "the price actually charged, net of discounts" — nothing bounds it. Merchandising operations acts on the rows by reconciling with the producing service. Cost is proportionate: these rows are expected to be rare, the table stores five small columns and is served from Postgres like the rest of the pipeline.
- **DQ_Orders_NonUSD_Currency** (data quality). Input: the deduplicated order table. One row is one order whose `currency` is present and not `USD`, carrying `order_id`, `currency` and `ordered_at`, ordered by `ordered_at` descending then `order_id` ascending, filterable by `currency`. Impact on this job: currency conversion is out of scope (SC-OUT) and the pipeline sums `quantity * unit_price` as if every order were USD (OQ-4). If multi-currency orders do exist, every affected product-hour is silently wrong, and no other signal exists. The condition can occur because `currency` is an optional free-form payload field with no upstream validation. Finance acts on it by deciding whether conversion must be brought into scope. Cardinality is bounded by the number of non-USD orders, which is assumed to be zero in production, so cost and noise are near zero while the assumption holds — and the table is precisely the alarm that tells us the assumption broke.
- **OB_OrderIngestionStats** (observability statistics). Input: the raw source stream, before deduplication and before the revenue filters. One row is one hour of `ordered_at` (1-hour tumbling window) with the count of received records and the count of distinct `order_id` values, ordered by window time descending, filterable by nothing beyond the time ordering. What it shows that platform metrics do not: the gap between received records and distinct orders is the **duplicate rate** of the at-least-once topic, which is the one upstream behaviour this pipeline is built to absorb; a sudden rise means the producer is retrying heavily, and a missing hour or a collapsed count means ingestion stopped while the aggregate quietly keeps serving the last complete hours. Operations acts on a missing or anomalous hour. Cost is one small row per hour.

**Skip**

- **Records dropped for being past the lateness tolerance.** FR-6 makes this an intentional exclusion, and Flink already exposes the dropped count through its `numLateRecordsDropped` window-operator metric. A SQL-level capture would have to compare `ordered_at` against the current watermark, which is non-deterministic in snapshot tests and would double-report what the runtime metric already shows. Not built.
- **Null or empty `items`.** The requirements state "`items` is never empty" and the schema declares the array non-null; an empty array simply contributes no lines and cannot corrupt a sum. No action would follow from such a row. Not built.
- **Null `customer_id`.** Documented and expected (guest checkout); the field is not used by any computation and is never exposed (NFR-4). Not built.
- **Unknown `product_id`.** There is no product dimension in this project (EK-3, OQ-5), so there is nothing to validate against and no join that could silently drop a row. Not built.
- **Per-source record counts beyond the one topic.** There is exactly one source; a second counting table would duplicate `OB_OrderIngestionStats`. Not built.

**Reuse**

- Nothing. The repository contains no catalog and no sibling project (see `## Current Project State`), so no existing data-quality or observability table covers this source.

## Technical Decisions

- **Project layout and naming.** One sub-project named `orders_revenue`, main script `orders_revenue.sqrl`, connectors under `connectors/` with the schema-plus-environment split (`sources.sqrl`, `sources-prod.sqrl`, `sources-test.sqrl`), test data under `connectors/test-data/`, API tests under `orders_revenue-api/tests/`, snapshots under `snapshots/orders_revenue/`. Reason: this is the layout the connector and test skills prescribe and the `event_processing` template already follows, and it keeps the environment choice to a single config variable.
- **External Kafka source, not a DataSQRL-managed internal topic.** The `orders` topic is produced by an upstream system and the API is read only (SC-OUT), so there is no mutation to expose; an internal `engine(kafka)` table would create an ingestion endpoint the requirements forbid. Consequence: the `kafka` engine is not enabled.
- **Engine set `flink`, `postgres`, `vertx`.** Flink runs the stream processing; Postgres serves the two query endpoints, the aggregate index and the monitoring tables; Vert.x serves GraphQL, REST and MCP. No subscriptions or mutations means no Kafka engine; the data volume (hourly rows per product for 13 months) does not justify Iceberg and its query engines.
- **Lateness tolerance implemented by the source watermark, 5 minutes.** TS-2 fixes the tolerance at 5 minutes and TS-3 forbids processing time. A watermark of `ordered_at` minus 5 minutes makes the window operator accept everything within the tolerance (FR-5) and drop everything beyond it (FR-6) without any extra filter, and keeps the decision in one place that both environments share.
- **1-hour tumbling window, not cumulative.** TR-3 and FR-3 specify a tumbling hour and the acceptance criteria compare whole-hour totals; a cumulative window would emit intermediate partial hours and change the snapshot shape and the meaning of `hour`. Consequence: a product-hour becomes visible after the watermark passes the hour end, i.e. about 5 minutes after the hour boundary, so the 30-second freshness of NFR-1/FR-1 is met by the `Orders` path and not by the aggregate path. This trade-off is forced by the 5-minute tolerance and is recorded in `## Assumptions`.
- **Two deduplication operators, one per consumer.** The served order table uses the SQRL deduplication that keeps the latest `ordered_at` per `order_id`, which is exactly FR-2 and produces versioned state. The revenue path instead uses a first-row deduplication over the same key ordered by `ordered_at` ascending, because the window table-valued function requires an insert-only input and the latest-wins form emits retractions. Consequence: if a retry ever carried different `items` than the first copy, revenue would reflect the first copy while the `Orders` endpoint shows the latest one; retries are producer resends of the same event (the source section says records are immutable events), so the copies are assumed identical.
- **Invalid line amounts excluded from revenue, captured instead.** A line with a non-positive `quantity` or a negative `unit_price` is filtered out of the revenue path and lands in `DQ_OrderLine_Invalid_Amount`, because letting it through would silently distort a product-hour sum that nobody can audit.
- **`customer_id` ingested but never projected.** NFR-4 forbids exposing it; keeping it on the ingested table preserves future options, and every API-facing definition omits it.
- **Hour semantics are UTC.** OQ-3's recommended default, consistent with `ordered_at` being UTC (TS-1); no timezone conversion is applied anywhere.
- **`limit` is the generated endpoint argument.** The requirements list `limit: Int` as a parameter of `HourlyProductRevenue`; DataSQRL already generates `limit` and `offset` arguments for query endpoints, so declaring a function argument with the same name would collide. The caller-visible contract keeps the name `limit`, which is why this is a deviation in form only; it is recorded here because it changes how the parameter is declared, not how it is called.
- **Optional query parameters by null-tolerant predicates.** All parameters of both operations are optional (API contract), so each filter is applied only when its argument is non-null rather than through required `query_by_all` arguments.
- **Indexing and retention.** A descending composite index on `product_id` and `hour` matches the only aggregate access pattern (FR-4). Retention follows NFR-3: 30 days for deduplicated orders, 13 months for hourly aggregates, with the Flink state time-to-live set in the production overlay so the deduplication state cannot grow without bound at 3.5M orders/day.
- **Test environment mirrors production.** The test connector is a filesystem stand-in reading JSONL with the identical table name, identical watermark column and identical 5-minute interval, so the lateness behaviour under test is the production behaviour; no `now()` column is introduced anywhere.

## Assumptions

- **Refunds and cancellations (OQ-1)**: Assumed revenue is gross of refunds and no refund or cancellation stream is consumed. Rationale: the requirements put refunds out of scope and recommend this default explicitly. [impact: high]
- **`unit_price` semantics (OQ-2)**: Assumed `unit_price` is net of discounts and tax exclusive, used as-is in `quantity * unit_price`. Rationale: the source section states "`unit_price` is the price actually charged, net of discounts" and the open question recommends this default. [impact: high]
- **Freshness of the aggregate path (NFR-1/FR-1 vs TS-2/FR-5)**: Assumed the 30-second freshness target applies to an order becoming queryable through the `Orders` endpoint, while a product-hour in `HourlyProductRevenue` becomes visible once the watermark passes the hour end (about 5 minutes after the hour boundary). Rationale: a 5-minute lateness tolerance and sub-30-second window emission are mutually exclusive on event time, and the stated acceptance criterion for FR-1 is "returned by the API", which the order lookup satisfies. [impact: medium]
- **Meaning of "late within tolerance" (FR-5)**: Assumed an event is inside the tolerance when its `ordered_at` lags the current maximum observed event time by at most 5 minutes, which is exactly the watermark condition. Rationale: this is the only event-time definition a Flink watermark can express, and it reproduces both acceptance cases (2 minutes in, 20 minutes out). [impact: medium]
- **Retry copies are byte-identical in `items` (FR-2 / revenue path)**: Assumed a producer retry repeats the same order lines, so the first-row deduplication used by the revenue path and the latest-wins deduplication used by the served order table yield the same revenue. Rationale: the source describes immutable events with at-least-once delivery, not updates. [impact: medium]
- **Hour boundary timezone (OQ-3)**: Assumed UTC. Rationale: the recommended default, and `ordered_at` is UTC. [impact: medium]
- **Multi-currency (OQ-4)**: Assumed every order is USD and `currency` is ignored in the revenue computation, with `DQ_Orders_NonUSD_Currency` raising the alarm if that is false. Rationale: the recommended default plus a cheap detector instead of an untestable conversion path. [impact: medium]
- **Product dimension (OQ-5)**: Assumed none; the API returns `product_id` only. Rationale: the recommended default and no product source exists in the repository. [impact: low]
- **Numeric type of `unit_price` and `revenue`**: Assumed `DECIMAL(10,2)` for `unit_price` and a decimal sum for `revenue`, matching the two-decimal sample values. Rationale: money must not be summed in floating point, and the sample payload shows two decimal places. [impact: medium]
- **Environments**: Assumed two environments, `test` (filesystem test data) and `prod` (Kafka), with no separate `local` or `dev` overlay. Rationale: the requirements describe only a production deployment and a test run; a local overlay can be added later without touching pipeline logic. [impact: low]
- **Kafka connection parameters**: Assumed bootstrap servers, the consumer group suffix and any SASL credentials come from environment variables, with credentials in the secret variable form, and the topic name `orders` hardcoded. Rationale: the requirements name only the topic; everything else differs per deployment and must not be written into build artifacts. [impact: low]
- **API access control**: Assumed no authentication or authorization is configured (public within the internal network), and no JWT claims are mapped. Rationale: stated directly in the API surface section, and no tenant field exists in the payload. [impact: medium]
- **Test record identifiers and values**: Assumed the concrete order ids, customer ids, product prices and timestamps enumerated in `## Test Data Specification`, since the requirements specify the edge cases but not their values. Rationale: the cases listed in the requirements are reproduced one-for-one, and the derived aggregate table is the snapshot oracle. [impact: low]
